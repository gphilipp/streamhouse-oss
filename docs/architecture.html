Architecture · milestone 1

Streamhouse OSS architecture

An open source streamhouse: operational data is captured as it changes, transformed continuously, and served both as Iceberg tables for analytics and as real-time context for applications and AI agents. Everything is declared in SQL and kept running by a control plane.

Overview

The system follows the five streamhouse stages: capture changes from databases, transport them as ordered events, transform them continuously, govern who can see what and where it came from, and serve the current state.

Two planes keep the design simple. The data plane is made of established projects (Debezium, Kafka, Flink, Iceberg) connected only through Kafka topics. The control plane is new code: it stores what you declared in SQL and continuously reconciles every component towards it, so the same SQL script can be re-run safely and a crashed job comes back on its own.

Capabilities and components

Each of the five streamhouse capabilities is provided by one or more components. Four components serve two capabilities at once, which is why the stack has fewer parts than a one-tool-per-stage design would suggest.

How a change travels

Follow one order from the demo. Customer 42 places it in the shop database; about a second later the support agent can answer about it, and within ten seconds it is in the Iceberg tables analysts read. Use the controls, or click a step, or open it on its own page.

    The control plane
    
      
    You describe the pipeline in SQL. The control plane parses it, stores it as desired state, and a reconcile loop drives each component towards it. Status and lineage flow back, and shctl sql --wait blocks until every resource is ready or has failed.
    
    
    
    
    
    
      
    
        
    The SQL surface
    
        
    One script declares the whole pipeline: CREATE CONNECTION, CREATE SOURCE, CREATE MATERIALIZED VIEW, CREATE STATEMENT (any Flink SQL), ALTER TOPIC … ENABLE ICEBERG | CONTEXT, GRANT, plus SHOW, DESCRIBE and DROP. Embedded Flink SQL is kept verbatim and handed to Flink.
    
      
    
      
    
        
    One Flink path
    
        
    Every Flink job reads and writes topics through the topic catalog, so there is one definition of what a topic looks like as a table. A materialized view is shorthand for CREATE TABLE … AS SELECT. Jobs are named after a hash of their SQL: a changed definition gets a new job and the old one is cancelled.
    
      
    
    
    
  
    

  
    
    
    
      
    The context engine
    
      
    The context engine turns any topic with a schema into a table that agents can query in milliseconds. It writes each batch of records and the next Kafka offsets in the same Postgres transaction, so the table is exactly-once with respect to the topic: after a crash it resumes from the offsets stored with the data.
    
    
    
    
    
    
      
    Lightning queries and governance
    
      
    Agents get three MCP tools, listTopics, getMetadata and queryData. Queries are a single-table subset of SQL: filters, ordering, limits and simple aggregates. Apache Calcite parses and validates each query, which is then re-rendered against Postgres with every literal bound as a parameter, run read-only with a timeout.
    
      
    Callers authenticate with an OIDC token or an API key and secret, which the engine exchanges for a token. A table is visible only to roles granted it, and every query, allowed or refused, is written to an audit table.
    
    
    
  
    

  
    
    
    
      
    Stack decisions
    
      
    Every choice favours a mature, Apache-licensed project over writing our own. New code exists only where no project covers the need, and is marked below.

    Known limits and next steps
    
    
      
      
    • Kafka runs without authentication on the internal network. Next: OAuth on Kafka with ACLs derived from grants.
      • 
      
    • One context engine instance. Next: partition assignment across instances, and a pluggable store.
      • 
      
    • Grants are enforced by the context engine and not yet pushed into Gravitino's access control.
      • 
      
    • A changed view query reprocesses its inputs from the start; new topic columns are not yet added to Iceberg tables.
      • 
      
    • Not yet built: Helm charts, a web UI, column masking and row filters.
